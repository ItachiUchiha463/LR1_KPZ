## 1. Огляд архітектури

```
┌──────────┐     REST API      ┌──────────────┐     pymongo     ┌───────────┐
│  /docs   │ ───────────────→  │  backend/    │ ───────────────→ │  MongoDB  │
│(браузер) │ ←─────────────── │  (FastAPI)   │ ←───────────────  │(2 колекції)│
└──────────┘                   └──────────────┘                  └───────────┘
                                       │
                                       │ читає
                                       ▼
                              ┌──────────────────┐
                              │ inference_engine/ │
                              │  (машина виводу)  │
                              └──────────────────┘
```

Три частини:

| Частина | Призначення | Залежності |
|---|---|---|
| `backend/` | REST API над MongoDB: CRUD правил/фактів, запуск діагностики, валідація | FastAPI, pymongo |
| MongoDB | Зберігання бази знань: колекції `rules`, `facts` | Atlas або локально |
| `inference_engine/` | Власне діагностика | чистий Python, без залежностей |

Окремого візуального редактора немає — усе керування базою знань
відбувається через автоматично згенеровану Swagger-документацію на
`http://localhost:8000/docs`.

## 2. Встановлення з нуля

### 2.1. MongoDB

Через **MongoDB Compass** підключитись до сервера — локального
(`mongodb://localhost:27017`) або **MongoDB Atlas** (хмара).

Для Atlas:
1. `Database → Connect → Drivers → Python` — скопіювати connection string
2. **Обов'язково** `Network Access → Add IP Address` — без цього кроку
   з'єднання відхиляється ще до автентифікації
3. Якщо в паролі є символи `@ : / ? # [ ]` — URL-encode їх

Створювати колекції вручну не потрібно — це зробить `seed_kb.py`.

### 2.2. Python-залежності

```bash
cd backend
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux / macOS:
source .venv/bin/activate

pip install -r requirements.txt
```

Якщо встановлення падає на збірці `pydantic-core` (Rust/PyO3) — ваш Python
новіший за той, під який зібрано доступні wheel-файли. У `requirements.txt`
стоять мінімальні межі версій (`>=`), тому найчастіше допомагає:

```bash
pip install --upgrade pip
pip install -r requirements.txt --upgrade
```

### 2.3. Налаштування з'єднання

```bash
cp .env.example .env
```

Вставити реальний `MONGO_URI`, наприклад:

```
MONGO_URI=mongodb+srv://user:pass@cluster0.xxxxx.mongodb.net/?retryWrites=true&w=majority
MONGO_DB=expert_system
```

### 2.4. Заповнення бази знань

```bash
python seed_kb.py
```

Читає `data/knowledge_base.json` (125 правил, 70 фактів — уже згенеровано)
і заповнює дві колекції MongoDB: `rules`, `facts`. Якщо колекції вже
містять дані, скрипт запитає підтвердження. Для автоматичного перезапису:
`python seed_kb.py --force`.

Якщо потрібно перегенерувати саму базу знань:

```bash
cd ../data
python gen_kb.py
cd ../backend
python seed_kb.py --force
```

## 4. Керування базою знань через /docs

На `/docs` — інтерактивна Swagger-документація FastAPI. Кожен ендпоінт
можна розгорнути, натиснути **Try it out**, заповнити поля й виконати —
без curl і без написання коду.

### 4.1. Перегляд правил

`GET /api/rules` — список усіх правил. Параметри `branch`, `layer`,
`search`, `enabled_only` дозволяють фільтрувати без завантаження всіх 125
одразу.

### 4.2. Створення правила

`POST /api/rules`, приклад тіла запиту:

```json
{
  "id": "Пр-нове",
  "branch": "RAM",
  "layer": 1,
  "conditions": [
    {"fact": "доступна_памʼять_%", "op": "<", "value": 20}
  ],
  "conclusions": [
    {"fact": "тиск_на_памʼять", "value": "підвищений"}
  ],
  "text": "",
  "note": "",
  "enabled": true
}
```

Поле `text` можна лишити порожнім — головне, що читає машина виводу, це
`conditions`/`conclusions`. Pydantic одразу перевірить формат (наприклад,
чи `op` — дозволений оператор) і поверне зрозумілу помилку `422`, якщо
щось не так.

### 4.3. Редагування й видалення

`PUT /api/rules/{mongo_id}` — оновити, `DELETE /api/rules/{mongo_id}` —
видалити. `mongo_id` береться з поля `_id` у відповіді `GET /api/rules`.

### 4.4. Вимкнення замість видалення

`POST /api/rules/{mongo_id}/toggle` — перемикає `enabled`, не видаляючи
правило. Корисно для перевірки "що буде, якщо прибрати це правило", не
втрачаючи текст.

### 4.5. Факти

Аналогічний CRUD на `/api/facts` — `name`, `kind` (`raw`/`derived`),
`aggregation` (`single`/`collect`/`max`), `type`, `unit`.

## 5. Перевірка бази знань на коректність

`GET /api/kb/validate` — статичний аналіз без запуску діагностики,
повертає шість перевірок:

| Перевірка | Що означає провал |
|---|---|
| `unknown_facts_in_conditions` | Правило посилається на факт, якого немає в описі |
| `unknown_facts_in_conclusions` | Те саме для правої частини правила |
| `duplicate_rule_ids` | Два правила мають однаковий `id` |
| `rules_without_conditions` | Правило спрацює завжди — майже напевно помилка |
| `bad_operators` | Використано оператор поза списком підтримуваних |
| `unreachable_facts` | Факт очікується в умовах, але жодне правило його не виводить |

Блок `summary` дає зведену статистику: кількість правил, фактів,
скільки реально використовується й виводиться.

`POST /api/kb/reload` — скидає внутрішній кеш бази знань, якщо базу
змінили напряму через MongoDB Compass, минаючи API.

## 6. Запуск діагностики

### 6.1. Через /docs (основний спосіб)

`POST /api/diagnose`, приклад тіла запиту:

```json
{
  "facts": {
    "доступна_памʼять_%": 6,
    "кількість_swap_операцій": 500,
    "тренд_використання_RAM": "монотонно_зростає",
    "тривалість_симптому_хв": 45,
    "критичність_сервісу": 5
  },
  "include_trace": true,
  "save_run": true,
  "label": "перевірка витоку памʼяті"
}
```

`save_run: true` записує прогін у колекцію `runs`, доступну потім через
`GET /api/runs` (список) і `GET /api/runs/{run_id}` (повні деталі з
трасуванням). Без `save_run` прогін виконується, але ніде не зберігається.

### 6.2. Через curl

```bash
curl -X POST http://localhost:8000/api/diagnose \
  -H "Content-Type: application/json" \
  -d '{"facts": {"доступна_памʼять_%": 6, "кількість_swap_операцій": 500, "тренд_використання_RAM": "монотонно_зростає"}}'
```

### 6.3. Напряму через Python (для скриптів і тестів)

Якщо MongoDB піднімати не хочеться — можна працювати зі статичним
`data/knowledge_base.json` без бекенда взагалі:

```python
import json
from inference_engine.engine import InferenceEngine

with open("data/knowledge_base.json", encoding="utf-8") as f:
    kb = json.load(f)

engine = InferenceEngine(kb, neural_runner=None)

result = engine.run({
    "доступна_памʼять_%": 6,
    "кількість_swap_операцій": 500,
    "тренд_використання_RAM": "монотонно_зростає",
    "тривалість_симптому_хв": 45,
    "критичність_сервісу": 5,
})

print(result.diagnoses())    # ['memory_leak_critical']
print(result.severity())     # 'SEV1'
```

## 7. Інтерпретація результатів

| Поле відповіді | Зміст |
|---|---|
| `diagnoses` | Список усіх знайдених діагнозів (може бути кілька одночасно) |
| `severity` | Фінальний рівень інциденту (`SEV1`…`SEV4`) після ескалації за тривалістю |
| `facts` | Повний знімок робочої пам'яті — усі проміжні факти |
| `conflicts` | Логічні конфлікти в базі знань (два правила дали різні значення `single`-факту) — у справній базі завжди порожній список |
| `missing_raw_facts` | Які вхідні показники не були подані — гілки, що їх потребують, просто не спрацювали |
| `trace` | Повний журнал: яке правило коли спрацювало і що вивело |

### 7.1. Пояснення конкретного діагнозу (через Python)

```python
chain = engine.explain(result, "діагноз")
for step in chain:
    print("  " * step["depth"], step["rule_id"], ":", step["text"])
```

Ланцюжок правил від кінцевого діагнозу назад до сирих вхідних даних —
"чому система так вирішила", на відміну від чорної скриньки.

### 7.2. Перегляд збережених прогонів

```bash
curl http://localhost:8000/api/runs                 # список, найновіші перші
curl http://localhost:8000/api/runs/<run_id>         # повні деталі з трасуванням
```

## 9. Типові несправності

| Симптом | Причина | Рішення |
|---|---|---|
| `ModuleNotFoundError: No module named 'kb_service'` | `uvicorn` запущено не з папки `backend/` | `cd backend`, потім `uvicorn main:app ...` |
| `mongo_connected: false` | Atlas: IP не додано в Network Access; локально: mongod не запущено | Перевірити Network Access в Atlas / запустити mongod |
| `422 Unprocessable Entity` при збереженні правила | Умова не пройшла Pydantic-валідацію | На `/docs` під формою одразу видно, яке саме поле некоректне |
| `409 Conflict` при створенні правила | `id` уже зайнятий іншим правилом | Обрати інший id, або відредагувати наявне правило |
| pip не може зібрати `pydantic-core` | Занадто нова версія Python, немає готового wheel | `pip install --upgrade pip`, або venv на Python 3.12/3.13 |
| Діагноз не з'являється при "поганих" вхідних даних | Не всі сирі критерії подані | Перевірити `missing_raw_facts` у відповіді |

## 10. Автоматизоване тестування

```bash
python -m tests.test_engine
```

43 перевірки, включно з:
- статичною валідацією бази знань (50–150 правил, немає невідомих фактів)
- "здоровою" системою (жодного хибного діагнозу)
- критичними сценаріями (одиночний і множинний діагноз одночасно)
- міжгруповими правилами (CPU-гілка використовує факт із гілки диска)
- пояснюваністю (`engine.explain()`)
- ескалацією рівня інциденту за тривалістю симптому
- стійкістю до некоректних/неповних вхідних даних
- детермінованістю (той самий вхід завжди дає той самий вихід)

Рекомендується запускати тести після будь-якої зміни в `inference_engine/`,
а також після масової зміни правил через `data/gen_kb.py`.
